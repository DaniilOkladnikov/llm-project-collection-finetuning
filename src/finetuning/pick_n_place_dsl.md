# Pick-and-Place DSL

A DSL the LLM emits to drive a pick-and-place robot. The LLM is the only stateful component. Every value the next invocation needs appears in the current invocation's output; the system keeps the most recent of each block in context plus turn history.

---

## 0 Assumptions

- Scene changes during turn execution have no effect on execution. Every change in scene between turns is told to the model explicitly.
- Tasks given by user may have wrong assumptions about the scene state, but are unequivocal for any scene configuration.

---

## 1. Execution model

### 1.1 Vocabulary

- **Conversation**: Collection of turns. Is interrupted by user (starting new conversation). `scans`, `position`, `gripper`, `held` carry across turns.
- **Turn**: one user prompt and the model's response. May span many invocations.
- **Invocation**: one LLM forward pass.
- **Step**: one numbered unit in PROGRAM. One step = one invocation.
- **This turn**: after the last user message
- **Location** is a single slot in the scene, can only contain one object at most
- **Location Collection** is name of a group of one or more Locations
- **Target** is a **Location** or multiple **Location** or **Location Collection** or multiple **Location Collection**


### 1.2 Context manager and Blocks.

There are messages of only two roles: `ASSISTANT` and `USER`. Note, I don't use typical tool message role, instead write tool results as special blocks into assistant messages.

For `ASSISTANT` messages, there is no freeform text, everything is in some block. There are blocks, that the model generates and that can be passed to the model as input context, in this order: `PRECALL` `MAP` `STATE` `PROGRAM` `RESOLUTION` `MEMORY` `TOOLS` `OUTCOME` `CHECK` `ERROR` `ANSWER` in this exact order. And there are two blocks that are tool return values, they can be passed to the model: `PRECALL RESULTS` `TOOLS RESULTS`, not generated by it.

The **Context manager** is a program that parses and keeps track of the blocks and user messages and passes the right input to the model based on conditions described below. It NEVER parses the content of the blocks. It also makes tool calls, one by one, updating tools results after each tool call and invoking the model. Updating some block counts even if the content isn't changed, if it was generated by the model, its an update, even if the content was empty and stays empty.

These blocks may be empty: `MAP` `TOOLS` `CHECK` `ERROR` `PRECALL RESULTS` `TOOLS RESULTS`. All the other blocks cannot be empty. If model generates one of them, then with content.

### 1.3 Input combinations

Blocks are added in the order shown. For blocks, if not stated explcitly otherwise, it is meant, that the model receives the most recent state of block, not all previous.

| # | Input |
|---|--------|
| I1 | all previous pairs role `USER` message - `ANSWER` block + most recent role `USER` message + those of `PRECALL` `PRECALL RESULTS` `MEMORY` that were generated this conversation|
| I2 | `TOOLS` `TOOLS RESULTS` or `PRECALL` `PRECALL RESULTS`, depends on what was generated last| 
| I3 | if `OUTCOME` was generated this turn: all previous pairs role `USER` message - `ANSWER` block + most recent role `USER` message + those of `PRECALL` `PRECALL RESULTS` that were generated this conversation + `MAP` `STATE` `PROGRAM` `MEMORY` + if `TOOLS` `TOOLS RESULTS` were generated this turn: `TOOLS` `TOOLS RESULTS` + (if `ERROR` was generated this turn: `ERROR`, elif `OUTCOME` was generated this turn: `OUTCOME`)| 

### 1.4 Output combinations

Exactly one of these per invocation. Blocks are emitted in the order shown. In "Optional: BLOCK1, BLOCK2,..." optionality only refers to first BLOCK1. 

| # | Output |
|---|--------|
| O1 | `PRECALL` |
| O2 | `MAP` `STATE` `PROGRAM` `RESOLUTION` optional: `MEMORY` `TOOLS` optional: `OUTCOME`|
| O3 | `CHECK`|
| O4 | `ERROR`|
| O5 | `STATE` `RESOLUTION` optional: `MEMORY` `TOOLS` optional: `OUTCOME`|
| O6 | `STATE` `ANSWER` |

### 1.5 System Loop

Here is how **Context manager** decides what type of input to give to the model. Reaching **O6** stops the loop and ends the turn.

| Input | Possible Outputs (Model decides) |
|---|--------|
| **I1** | **O1** or **O2**|
| **I2** | **O3** or **O4** |
| **I3** | **O5** or **O6** | 

| Previous Output | Condition | Input |
|---|--------|--------|
| **O1** | - | **I2** |
| **O2** | if `TOOLS` is not empty | **I2** |
| **O2** | if `TOOLS` is empty | **I3** |
| **O3** | if previous input this turn not counting **O3** was **O1** | **I1** |
| **O3** | if previous output this turn not counting **O3** was **O2** or **O5** | **I3** |
| **O4** | - | **I3** |
| **O5** | if `TOOLS` is not empty | **I2** |
| **O5** | if `TOOLS` is empty | **I3** |
 
Explanation:
1. The model can make precalls that last during whole conversation **I1**, **O1**
2. After that the model generates mapping and program + usual state, resolution and tool calls: **O2**.
3. **I2** is tool error handling step. Both precalls and tool calls go through it.
4. **I3**->**O5**->**I2**->**O3**->**I3** is the most common program execution routine with tool calls.
5. **I3**->**O6** happens when `OUTCOME` or `ERROR` was generated and ends the program with `ANSWER`

### 1.6 Block format

Each block has the form:

```
BLOCK_NAME
<content>
```

The next block's header on its own line ends the previous block. An empty block is its header followed immediately by the next header.

## 2. PRECALL Block

This is essentially a tool call that only differs from `TOOLS` blocks in that it is preserved and passed to the model across turns. The model uses it for tool calls, which results it needs to save. In my case it is get_positions().

```
PRECALL
get_positions()
```

## 2.5 MEMORY block

```
MEMORY
<Name>: <Value>, ...
```

The rule for this block is following: after model created it this conversation, it get's added to the input I1 and I3, the model only reemits this block when it wants to change it, otherwise the model doesn't reemit it. Model can add new names to memory and can change values of existing, but cannot delete old ones (cannot not reemit them).

## 3. STATE block

```
STATE
cursor: step_<N> | answer_<K> | error
position: <Position> | unknown
gripper: open | closed | unknown
held: <ObjectType> | none | unknown
scans: { <Location>: <ObjectType>, ... }
visited: [<Position>, ...]
```

Field semantics:
- **scans**: cumulative conversation-scoped map of *occupied* slots observed so far. A location covered by some pose in `visited` but absent from `scans` is **known empty**.
- **visited**: observe poses executed in the current turn. Reset each turn.

### 3.1 Tool effects on STATE

| Tool | Effect |
|------|--------|
| `move_to(P)` | `position := P` |
| `locate_shapes()` | append current `position` to `visited`; merge returned `slot → type` into `scans`; remove from `scans` any slot covered by the current pose but absent from the return |
| `open_gripper()` | `gripper := open`, `held := none` |
| `close_gripper()` | `gripper := closed`; `held := T` from the current `pick_<T>_<L>` pose or from the most recent move_to tool call argument if executed via pick primitive or from the user message if executed via get from user primitive, unknown otherwise |
| `get_gripper_state()` | `gripper := <return>`; if `open`, `held := none` |
| `get_position_state()` | `position := <return>` |

After a successful `pick X from L`: `scans[L]` is removed.
After a successful `place X at L`: `scans[L] := X`.

The model applies these effects when rewriting STATE for the next invocation.

User-stated state changes ("you are holding a cube") are applied directly: the model writes the corresponding STATE update in the same invocation it emits the program.

---

### 3.2 Cursor advancement rules

1. Cursor starts with step_1 when the program is emitted
2. If cursor in the input shows at ```step_<N-1>```, in the output it must show at ```step_<N>```.
3. Regardless of the rule 2 cursor shows at ```answer_<K>``` or ```error``` if input contains block **OUTCOME** with content ```answer_<K>``` or block **ERROR** 

## 4. MAP

Translates user-prompt phrases for objects and locations into scene-canonical names or lists thereof.

```
MAP
<phrase> = <value>
<phrase> = <value>
```

`<value>` is either a single canonical name or a bracketed list `[name1, name2, ...]`.

### 4.1 Generation

For *every* distinct content noun phrase in the user prompt referring to an object type or a location, emit one MAP line — even when the phrase already matches a canonical name. Identity MAPs are intentional and uniform:

```
MAP
the cube = red_cube
red_cube = red_cube
the second bin = box2
box1 = box1
any drawer = [drawer1, drawer2, drawer3]
```

### 4.2 Inferring values from the position list

The scene provides only the position list. The model parses entries to infer entity structure: from `pick_red_cube_drawer1`, `pick_red_cube_drawer2`, `pick_red_cube_drawer3`, the model infers locations `drawer1`, `drawer2`, `drawer3` and, for "any drawer", produces `[drawer1, drawer2, drawer3]`.

Position-list entries may use any naming convention (`pick_red_cube_drawer1`, `drawer1_pick_red_cube`, etc.). The model identifies pick / place / observe entries by the name only.

### 4.3 What is *not* mapped

- **Pronouns** ("it", "the one I'm holding") — programs read STATE directly: `held`.
- **Numbers, kinds** — used inline in conditions.
- **"Somewhere" / "anywhere" with no inferable group** — no MAP line.

### 4.4 PROGRAM uses MAP phrases

PROGRAM uses MAP phrases (the left-hand sides) only — never raw MAP values. Values are expanded at resolution time.

## 5. PROGRAM
 
### 5.1 What a program is
 
A PROGRAM is an ordered sequence of numbered steps emitted as the `PROGRAM` block:
 
```
PROGRAM
STEP 1: <step body>
STEP 2: <step body>
...
STEP N: <step body>
```

The rule is **one step = one invocation**.

### 5.2 Lines of a program
 
Every line inside `PROGRAM` is exactly one of the following kinds. The interpreter parses by line role; each role has a fixed shape.
 
| Line kind | Shape |
|-----------|-------|
| Step header | `STEP <N>:` |
| Primitive line | `<primitive>` |
| Branching arm head | `when <cond>:` \| `otherwise when <cond>:` \| `otherwise:` |
| Outcome line | `answer_<K>` |
 
Indentation under a head line groups the primitives belonging to that head. The arm heads must each be followed by at least one indented primitive line or an outcome line.

### 5.2 Position-name pattern notation

`pick_<T>_<L>` and `place_<T>_<L>` denote position-list entries whose structure encodes "pick T at L" / "place T at L". The actual entry name is whatever the position list contains; the model finds it by structural match, not literal string construction.

### 5.3 Step kinds
 
A step body is exactly one of two kinds. The kind is determined by syntactic shape.
 
1. **Linear** — one or more primitive lines, no head. All primitives unwind into a single TOOLS batch.
2. **Branching** — one or more `when` / `otherwise when` arms, optionally followed by one `otherwise` arm. Conditions are evaluated in order; the first true arm wins. If none match and no `otherwise` is present, the step is `fallthrough` (no work; cursor advances). Arms inside of arms not allowed.


### 5.4 Position-name pattern notation
 
`pick_<T>_<L>`, `place_<T>_<L>`, and observe poses like `observe_<L>` denote entries in the position list whose structure encodes the action. The actual entry string is whatever the position list contains; the LLM finds the matching entry by structural match on `<T>` and `<L>`

### 5.5 Primitives
 
Every primitive is described by four facts: its **syntax**, the **tool calls** it unwinds to, the **RESOLUTION** lines it emits, and any **precondition** on STATE. 

`<X>, <W>` are always object types: either left hand sides in **MAP** or names derived from positions list.

`<A>, <B>` is always target: either left hand sides in **MAP** or names derived from positions list.

`<L> or <location>` is always single location: either left hand sides in **MAP** or name derived from positions list.

`<Position>` must always be a valid left hand side in the **MAP** that equals a valid position from the position list

#### 5.5.1 Simple actions
 
| Primitive | Tool calls | Resolution lines | Precondition |
|-----------|-----------|------------------|--------------|
| `go to <Position>` | `move_to(<Position>)` | (none) | — |
| `open gripper` | `open_gripper()` | (none) | — |
| `close gripper` | `close_gripper()` | (none) | — |
| `check gripper` | `get_gripper_state()` | (none) | — |
| `check position` | `get_position_state()` | (none) | — |
| `locate here` | `locate_shapes()` | (none) | — |

#### 5.5.2 Observe actions
| Primitive | Tool calls | Resolution lines | Precondition |
|-----------|-----------|------------------|--------------|
| `approach observe <A>` (drop `[]` if single argument) | For some observe pose `P` covering some location in `<A>`: `move_to(P)`. | `observe poses = [P1, P2, ...]` |
| `observe [<A1>, <A2>, ...]` (drop `[]` if single argument) | For each observe pose `P` covering some location in `<A1>, <A2>, ...` and `P ∉ STATE.visited`: `move_to(P); locate_shapes()`. | `observe poses = [P1, P2, ...]` |
| `observe everything` | For each observe pose in `get_positions` not in `STATE.visited`: `move_to(P); locate_shapes()`. | `observe poses = [P1, P2, ...]` |
| `observe next unvisited position` | `move_to(P); locate_shapes()` next `P` in order of positions list with `P ∉ STATE.visited` | `chosen_pose = P` |
| `observe next unvisited position not covering <A>` | As above, with the constraint that `P` covers no location in `<A>`. | `chosen_pose = P` |

#### 5.5.3 Pick and place actions
| Primitive | Tool calls | Resolution lines | Precondition |
|-----------|-----------|------------------|--------------|
| `approach pick of <X> at <A>` | `move_to(pick_<X>_<L>)` | (none beyond `<X>` / `<A>` helpers, if any) | none |
| `pick from <A>` | `move_to(pick_<X>_<L>); close_gripper()` | `L = <A> = <location>`<br>`T = scans[<L>] = <type>` | gripper open; `<A>` resolves to a single Location `L`; `L ∈ STATE.scans` |
| `get <X> from user` | `close_gripper()` | | |
| `approach place of <X> at <A>` | `move_to(place_<X>_<L>)` | (none beyond `<X>` / `<A>` helpers, if any) | `<L>` is known empty |
| `place at <A>` | `move_to(place_<X>_<L>); open_gripper()` | `L = <A> = <location>`<br>`X = held = <type>` | gripper closed; `STATE.held` is an ObjectType (not `none`, not `unknown`); `<A>` resolves to a single Location `L`; `L` is known empty 

#### 5.5.4 Memory

| Primitive | Effect | Resolution lines |
|-----------|--------|------------------|
| `remember <name> = <Expr>` | After the step's tool calls run, resolve `<Expr>` against the post-tools STATE and write the value to `MEMORY[<name>]`. | `<Expr> = <value>` if `<Expr>` is a helper; nothing if `<Expr>` is a literal. |

`<name>` from `remember <name> = <Expr>` can also be used by the model as temporary variable!

#### 5.5.5 Outcome
 
| Primitive | Effect | Resolution lines |
|-----------|--------|------------------|
| `answer_<K>` | Model should emit the OUTCOME block with content `answer_<K>` in the current invocation. The step's other primitives still run. The next invocation is the answer invocation. | (none) |

#### 5.5.6 Temporary variables

As opposed to memory, these are not written to memory block and not preserved across steps. Model only writes them in the resolution block.
 
| Primitive | Effect | Resolution lines |
|-----------|--------|------------------|
| `temp <name> = <expression>` | Model should emit `<name> = <expression value>` in the resolution block and use the variable further in the step | `<name> = <expression value>` |

A `temp` holding a Location or ObjectType helper may resolve to `none` (see §5.6, §5.7). Guard it with `if <name> is not none:` to act on the value. This lets a step compute a result **once** and branch on it, instead of testing existence with a condition and then recomputing the value to act on it.

### 5.6 ObjectType helpers

Each non-literal expression emits one RESOLUTION line of the form `<expression> = <value>`. A finder helper (`a type in <A>`, `a type in <A> other than <W>`, `a type shared by <A> and <B>`, `a type in <A> not in <B>`) resolves to `none` when no slot matches; capture it in a `temp` and guard with `if <name> is not none:`.

| Expression | Value |
|-----------|-----------------|
| literal type name (from MAP) | itself |
| `held` | `STATE.held`|
| `<memory_name>` | `MEMORY[<name>]` |
| `a type in <A>` | Let `L = first occupied in <A>`; value is `scans[L]`|
| `a type in <A> other than <W>` | Let `L` be the first slot in `<A>` (slot order) with `scans[L] ≠ <W>`; value is `scans[L]`|
| `a type shared by <A> and <B>` | value is first `X` in (types in `<A>`, slot order) such that some slot of `<B>` has `scans[·] == X` |
| `a type in <A> not in <B>` | value is first `X` in (types in `<A>`, slot order) such that no slot of `<B>` has `scans[·] == X` |

### 5.7 Location helpers

Each emits one RESOLUTION line of the form `<expression> = <value>` or `L/T = <expression> = <value>` in case of pick/place primitive expansion. A finder helper (`first empty in <A>`, `first occupied in <A>`, `first in <A> holding <X>`, `first holding <X>`, `first empty`, and their `outside`/`not` variants) resolves to `none` when no slot matches; capture it in a `temp` and guard with `if <name> is not none:`.
 
| Expression | Value |
|-----------|-----------------|
| literal Location name (from MAP) | itself; no resolution line |
| `<memory_name>` (storing a Location) | `MEMORY[<name>][0]`; emit `<memory_name> = <value>` |
| `first empty in <A>, <B>, ...` | First `L` in `<A>, <B>, ...` (position list slot order) that is covered by `STATE.visited` and absent from `STATE.scans` |
| `first occupied in <A>, <B>, ...` | First `L` in `<A>, <B>, ...` (slot order) present in `STATE.scans` |
| `first in <A>, <B>, ... holding <X>` | First `L` in `<A>, <B>, ...` (slot order) with `scans[L] == <X>` |
| `first in <A>, <B>, ... holding not <X>, <Y>, ...` | First `L` in `<A>, <B>, ...` (slot order) with `scans[L] != <X>, <Y>, ...` |
| `first holding <X>` | First `L` anywhere in `STATE.scans` (insertion order of `scans`) with entry `<X>` |
| `first holding <X> outside <A>, <B>, ...` | As above, excluding any `L` in `<A>, <B>, ...` |
| `first empty` | First `L` covered by `STATE.visited` and absent from `STATE.scans` (order: position-list order over all Locations) |
| `first empty outside <A>, <B>, ...` | As above, excluding any `L` in `<A>, <B>, ...` |

### 5.8 Conditions

Each evaluated condition emits one RESOLUTION line of the form `<cond> = <value>`. Value is bool unless stated otherwise
 
**Robot.**
 
| Condition | Value |
|-----------|-----------------|
| `gripper is open` | `STATE.gripper == open` |
| `gripper is closed` | `STATE.gripper == closed` |
| `gripper is known` | `STATE.gripper != unknown` |
| `holding anything` | `STATE.held` is an ObjectType (not `none`, not `unknown`) |
| `holding <X>` | `STATE.held == <X>` |
| `holding is known` | `STATE.held != unknown` |
| `at home` | `STATE.position == home` |
| `at <Position>` | `STATE.position == <Position>` |
| `position` | `STATE.position` (returns position name; used in comparisons) |
| `visited all observe positions` | exists no observe position not in `STATE.visited`|

**Targets**

| Condition | Value |
|-----------|-----------------|
| `<A> is empty` | A covered by visited and no `L ∈ <A>` is in `STATE.scans` |
| `<A> is not empty` | A covered by visited and there is `L ∈ <A>` is in `STATE.scans` |
| `<A> is full` | Every `L ∈ <A>` is in `STATE.scans` |
| `<A> has <X>` | Some `L ∈ <A>` has `scans[L] == <X>` |
| `<A> has no <X>` | No `L ∈ <A>` has `scans[L] == <X>` |
| `<A> contains only <X>` | `<A>` non-empty and every occupied `L ∈ <A>` has `scans[L] == <X>` |
| `count in <A>` | `\|{L ∈ <A> : L ∈ scans}\|` (numeric) |
| `count of <X> in <A>` | `\|{L ∈ <A> : scans[L] == <X>}\|` (numeric) |
| `count of empty slots in <A>` | `\|{L ∈ <A> : L covered by visited, L ∉ scans}\|` (numeric) |
| `empty slots in <A>` | List of `L ∈ <A>` known empty |
| `occupied slots in <A>` | List of `L ∈ <A>` in `scans` |
| `types in <A>` | Set of `scans[L]` for `L ∈ <A>` in `scans` |
| `count by type in <A>` | Map `{T → \|{L ∈ <A> : scans[L] == T}\|}` |
 
**Cross-target.**
 
| Condition | Value |
|-----------|-----------------|
| `more empty room in <A> than <B>` | `count of empty slots in <A> > count of empty slots in <B>` |
| `same count in <A> and <Z>` | `count in <A> == count in <Z>` |
| `types shared by <A> and <Z>` | `types in <A> ∩ types in <Z>` |
| `types in <A> not in <Z>` | `types in <A> \ types in <Z>` |
 
**Scene-wide** (read across all of `STATE.scans` and `STATE.visited`).
 
| Condition | Value |
|-----------|-----------------|
| `locations holding <X>` | List of every `L ∈ scans` with `scans[L] == <X>` |
| `no location holds <X>` | The above list is empty |
| `first holding <X> exists` | Some `L ∈ scans` has `scans[L] == <X>` |
| `first empty location exists` | Some `L` covered by `visited` is absent from `scans` |
| `every observe pose visited` | `STATE.visited ⊇ {observe poses in get_positions}` |
 
**Composition.** `and`, `or`, `not`, `>`, `>=`, `<`, `<=`, `==`, `+`, `-`.
 
A composite condition (e.g. `a and b`) should be emitted split:
 
```
a = <value>
b = <value>
a and b = <value>
```

## 6. RESOLUTION

Every step emits a `RESOLUTION` block:

```
RESOLUTION
<resolution lines>
selected: <selected>
<resolution lines>
```

Resolution happens going top-down through the step defined in the cursor as described in §5.

### 6.1 Selected: options
 
The LLM first resolves what it will execute using selected: and then resolves everything else top-down

| Step kind | Entry-phase lines |
|-----------|-------------------|
| Linear | `selected: linear` |
| Branching | For each condition evaluated in head order, stopping at the first true (or after all if none true): one line `<cond> = <value>`. Then either `selected: "<arm head text>"` (the arm head text without trailing colon, in double quotes) for the first true arm, or `selected: fallthrough` if none matched. |

---

## 7. TOOLS

```
TOOLS
move_to(observe_box1)
locate_shapes()
```

Each non-empty line is one tool call. Calls run in order; later calls in the same batch see effects of earlier ones.

An empty TOOLS block (just the header) is valid

---

## 8. OUTCOME and ANSWER

### 8.1 Outcome

Emitted in the same invocation as the step whose selected arm ends with `answer_<K>`.

```
OUTCOME
answer_<K>
```

### 8.2 Answer invocation

Triggered by `cursor: answer_<K>` or `cursor: error` in input STATE. The model emits combination O6:

```
STATE
cursor: answer_<K> | error
... (final field values, all tool calls applied that happened before the error one)

ANSWER
<natural-language reply>
```

The model composes prose by:

1. Looking up `answer_<K>` in the input PROGRAM to find its program location (which arm of which step terminates).
2. Reading STATE for the values needed in the reply.
3. Writing prose appropriate to the situation (success confirmation, refusal explanation, query response).

There are no tags. Register is determined by program context.

---

## 9. CHECK AND ERROR

After each tool call is executed, the model checks the result and emits either

```
CHECK
```
or
```
ERROR
```
